# magekwik-magento — user guide

The `magekwik-magento` plugin makes Claude Code a competent Magento Open Source 2.4 developer. It ships these:

| | What it is | How you use it |
|---|---|---|
| **8 skills** | Reference knowledge Claude loads on its own when a task touches that area | Just ask — "add an observer for order placement", "why is `setup:upgrade` slow?" |
| **`/magekwik-magento:init`** | Sets a project up so Claude behaves consistently in it | Run once per project, re-run after big changes |
| **`/magekwik-magento:review`** | A read-only Magento-aware code review of a diff, branch or PR | Run before you open a PR, or on someone else's |
| **`/magekwik-magento:local-setup`** | A guided, resumable setup of a running local store | Run once per local copy; re-run to resume |
| **`/magekwik-magento:audit cron`** | Works out a week of your cron schedule from its config and run history and writes a client-ready report with a proposed schedule | Run on a local copy; it never touches a live store |

Supported: **Magento Open Source 2.4.4 – 2.4.9 · PHP 8.1 – 8.5 · Luma and Hyvä**. Adobe Commerce-only features are referenced, not covered in depth.

---

## 1. Who it is for

**Developers and agencies working on Magento 2** — the plugin is built for people writing modules, themes, APIs and deployment scripts. It gives Claude the framework's conventions (so it stops reaching for `ObjectManager`, raw SQL or `InstallSchema`), the version-specific facts (what changed in 2.4.9's cache backend, which PHP each release needs), and a reviewer that reads a diff the way a senior Magento engineer would.

**Store owners and merchants** get the benefit indirectly today: better code from whoever works on the store, a review gate that catches the classic security and upgrade-breaking mistakes, and a repository that any developer (or Claude session) can pick up with the right context already in place. The plugin does not yet talk to a running store — see [Roadmap](#13-roadmap) for what is coming.

## 2. Install

**From this repository (self-hosted marketplace):**

```
/plugin marketplace add magekwik/claude-magento
/plugin install magekwik-magento@magekwik
```

While the repository is private, use the SSH form from a machine whose key has access:

```
/plugin marketplace add git@github.com:magekwik/claude-magento.git
```

**Try it without installing** (loads for one session, changes to skills take effect immediately):

```
claude --plugin-dir /path/to/claude-magento/plugins/magento
```

**Update:** `/plugin marketplace update magekwik` picks up new releases.

Requirements: Claude Code 2.1+, `git`, `bash`. Optional: `gh` (PR review), `vendor/bin/phpcs` with `magento/magento-coding-standard` (PHPCS findings in reviews).

## 3. First run: `/magekwik-magento:init`

Run it from the project root — the directory that contains `bin/magento`.

**What it detects** (Claude reads the project files directly; the plugin ships no scripts):

- Edition and version from `composer.lock`; the host PHP version
- Custom modules under `app/code` and themes under `app/design`, with each theme's parent
- Whether the store is Hyvä (theme parent chain or `hyva-themes/*` in `composer.lock`)
- The dev environment: **Warden**, **DDEV**, **Docker Compose**, **docker-magento**, or native — and therefore the right way to run `bin/magento`
- Tooling present: phpcs (`vendor/bin/phpcs` or `phpcs.xml*`), `phpstan.neon*`, `dev/tests/unit/phpunit.xml*`
- Deployment mode from `app/etc/env.php`

**What it writes — and nothing else:**

1. A block in `CLAUDE.md` between `<!-- magento:begin -->` and `<!-- magento:end -->`. If `CLAUDE.md` exists, only that block is touched; your other content stays. Example:

   ```markdown
   <!-- magento:begin -->
   ## Magento project (generated by the magento plugin v1.0.0 — rerun /magekwik-magento:init to refresh)

   - **Edition:** Magento Open Source 2.4.9 · host PHP 8.4.10 · mode: production
   - **Frontend:** Luma — themes: Acme/default → Magento/luma
   - **Custom modules:** Acme_Catalog (app/code/Acme/Catalog)
   - **Environment:** Warden — run CLI as `warden env exec php-fpm bin/magento …`
   - **Tooling:** phpcs ✓ · phpstan ✗ · phpunit ✓

   ### Working here
   - Use the CLI prefix above for every `bin/magento` and `composer` command.
   - After schema changes: `setup:db-declaration:generate-whitelist --module-name=<Module>`, then `setup:upgrade`, then `cache:clean`. …
   - Conventions Claude follows in this repo: `.claude/rules/magento.md`. …
   - Before finishing PHP changes: `vendor/bin/phpcs --standard=Magento2 <changed paths>`.
   <!-- magento:end -->
   ```

2. `.claude/rules/magento.md` — the conventions rulebook (section 5), trimmed to what applies: the Hyvä section is dropped on a Luma store and vice versa. Its first line marks it as generated. **Delete that first line to take ownership**; `init` will then leave the file alone on later runs.

**Re-running** is safe: the block is replaced in place, never duplicated. Commit both files — they are the project's memory for every future session.

**CLI prefixes it writes**

| Environment | Detected by | Prefix in `CLAUDE.md` |
|---|---|---|
| Warden | `.warden/` or `.env` with `WARDEN_ENV_TYPE=` | `warden env exec php-fpm bin/magento …` |
| DDEV | `.ddev/` | `ddev exec bin/magento …` |
| docker-magento (markshust) | compose file + `bin/clinotty` | `bin/magento …` (the project's wrapper) |
| Docker Compose | `compose*.yml` / `docker-compose*.yml` | `docker compose exec <php-service> bin/magento …` (edit the service name) |
| Native | none of the above | `bin/magento …` |

## 4. Everyday use: the skills

Skills are not commands. Each has a one-line description Claude sees in every session; when a request matches, Claude reads that skill's guide (a short hub) and, only if needed, its deeper reference files. You can also invoke one explicitly (`/magekwik-magento:module`) to load it for the conversation.

| Skill | Covers | Try asking |
|---|---|---|
| `magekwik-magento:conventions` | The rulebook: architecture, security, performance, Luma, Hyvä and quality rules, each with the *why* and the PHPCS sniff that enforces it | "Which rule says I can't add a column to `catalog_product_entity`?" |
| `magekwik-magento:module` | Modules, `di.xml` plugins/preferences/virtual types, events and observers, ViewModels, cron, console commands, admin controllers with ACL | "Add a before plugin that rejects cart quantities over 10" |
| `magekwik-magento:data` | `db_schema.xml` and the whitelist, data/schema patches, models and repositories, service contracts, EAV and extension attributes | "Store a brand on every product" |
| `magekwik-magento:api` | `webapi.xml` REST, GraphQL schema and resolvers, ACL, tokens, CSRF | "Expose GET /V1/acme/brands to store managers only" |
| `magekwik-magento:frontend-luma` | Layout XML, `.phtml` templates and escaping, ViewModels, RequireJS/Knockout, LESS, static deploy | "Add a free-shipping notice to the top of every page" |
| `magekwik-magento:frontend-hyva` | Tailwind, Alpine.js, ViewModels, private content, compatibility modules | "Make that banner dismissible on our Hyvä theme" |
| `magekwik-magento:ops` | `bin/magento` workflows, cache types, indexers, modes, logs, Xdebug, Varnish/LiteMage/Redis, upgrades and patches, Warden/DDEV/Docker | "What do I run after changing `db_schema.xml` in developer mode?" |
| `magekwik-magento:quality` | PHPCS with the Magento2 standard, PHPStan, PHPMD, unit and integration tests | "Set up PHPCS for `app/code/Acme` and give me a unit test skeleton" |

**How the rulebook works.** Every rule has an ID — `A1`–`A10` architecture, `S1`–`S6` security, `P1`–`P7` performance, `L1`–`L5` Luma, `H1`–`H5` Hyvä, `Q1`–`Q6` quality. The reviewer cites them, the other skills link to them, and `init` copies them into your project. A few you will meet often:

- **A1** — never `ObjectManager::getInstance()` outside factories, proxies and setup code
- **A6** — schema is declarative only (`db_schema.xml` + whitelist); no `InstallSchema`/`UpgradeSchema`
- **A7** — never edit `vendor/` or `app/code/Magento`, and never alter a core table's schema — extend with your own table, an EAV attribute or an extension attribute
- **S2** — a controller that changes state implements `HttpPostActionInterface`; GET never mutates
- **S3** — escape every template output with `$escaper->…`; `$block->escapeHtml` is deprecated
- **P3** — no `cacheable="false"` unless the whole page is private; per-user fragments go through customer-data sections or private content
- **H1** — on Hyvä there is no RequireJS, Knockout, jQuery or `x-magento-init`

Skills state their target range and, where behaviour differs between 2.4.4 and 2.4.9, say which version they mean. Every reference file ends with the documentation pages it was checked against.

## 5. `/magekwik-magento:review`

A read-only review by a dedicated subagent that reads the rulebook first, then the skills relevant to the touched files, then the diff.

| You type | It reviews |
|---|---|
| `/magekwik-magento:review` | Everything since the default branch: commits, staged and unstaged changes, plus new (untracked) code files |
| `/magekwik-magento:review develop` | The same, measured from the merge-base with `develop` |
| `/magekwik-magento:review 42` | GitHub PR #42 (needs `gh` logged in) |
| `/magekwik-magento:review 42 --comment` | …and posts each finding as an inline PR comment |

Untracked files are included only if they look like Magento code (under `app/`, `lib/`, `dev/`, `setup/`, `pub/` except static/media; text extensions; under 200 KB) — anything skipped is listed by name.

**What it looks for**, beyond running PHPCS when `vendor/bin/phpcs` and the Magento2 standard are present: `ObjectManager` use; plugins on `final`/`private`/`static` methods or an `around` that never calls `$proceed`; raw SQL; legacy install scripts; edits under `vendor/`; missing `ADMIN_RESOURCE` or `webapi.xml` resources; mutating GET actions; unescaped output; loads inside loops; `cacheable="false"`; `$this` in templates; Luma JS on a Hyvä theme; missing `strict_types`; `db_schema.xml` changed without the whitelist; patches without dependencies.

**Output format** — fixed, so it can be parsed and posted:

```
[blocker] app/code/Acme/Catalog/Controller/Index/Save.php:14 — A5
Why: `$name` is concatenated into the INSERT, so any request can inject SQL.
Fix: Drop the raw query; save through a repository, or at minimum use bound parameters.

[major] app/code/Acme/Catalog/Controller/Index/Save.php:7 — S2
Why: The action writes to the database but is reachable by GET with no form-key check.
Fix: Implement HttpPostActionInterface and POST to it with the form key.

Verdict: 1 blocker(s), 1 major, 0 minor, 0 nit — not mergeable as is
```

Severity: **blocker** = security or data loss · **major** = breaks in production or on upgrade · **minor** = maintainability · **nit** = style PHPCS does not catch. If PHPCS is not available it says so in one line rather than pretending it ran.

The reviewer never edits files. With `--comment`, it only ever writes PR comments.

## 6. `/magekwik-magento:local-setup`

Sets up a running local Magento store, one step at a time, and remembers where it got to.

```
/magekwik-magento:local-setup                                    # asks what it needs
/magekwik-magento:local-setup --dir ~/sites/shop --env warden --new --distro mage-os
/magekwik-magento:local-setup --repo git@github.com:acme/shop.git --db-dump .magento-local/db.sql.gz --media .magento-local/media.tar.gz
/magekwik-magento:local-setup --status                           # progress so far
/magekwik-magento:local-setup --reset                            # start again (deletes only the ledger)
```

**What it asks.** Where to set up; from what — your git repository, the latest Magento Open Source (needs Marketplace keys) or Mage-OS (needs none); for a repository, whether to install fresh or import a sanitised dump; and which tool — Warden, DDEV, docker-magento or Valet, recommended from what is installed. Arguments answer the questions ahead of time.

**The ledger.** Everything it decides goes into `.magento-local.env` in the target folder — git-ignored (`.git/info/exclude` in a repository, so your committed `.gitignore` is never edited) and created before anything else so you can change a value before the step that uses it.

**When it needs you, it stops.** Installing a tool, a `sudo` command (Warden's certificate, docker-magento's `/etc/hosts` line and TLS, `valet trust`), Marketplace keys, or a dump or media archive that is not there yet: the step is marked blocked, you get the exact commands, and re-running the command resumes at that step. It never runs `sudo` or a global installer itself, never asks you to paste keys into the chat, and never connects to a live store — real data only comes from a sanitised dump you place under `.magento-local/`.

**No real credentials.** The database and admin logins are local development defaults (Warden's, DDEV's and docker-magento's own), not secrets — the store runs only on your machine; change them in the ledger before step 7 if you like. Magento generates the encryption key itself, and the plugin never reads it or your Composer keys.

**Per tool:**

| Tool | Notes |
|---|---|
| Warden | Uses Warden's shared router on 80/443 and `*.test` DNS; signs a certificate (`sudo` on first use). |
| DDEV | Moves to free ports (e.g. 8080/8443) when 80/443 are taken, in `.ddev/config.local.yaml`; for Magento installs without keys, stops and gives you the command that sets your Marketplace keys in the project's `.ddev/homeadditions/.composer/` (git-ignored), then `ddev restart` (DDEV does not mount your Composer home; the plugin never looks for or touches your keys). |
| docker-magento | Copies markshust's template (no `curl \| bash`), follows its own install flow, moves busy ports in `compose.override.yaml`; you run `bin/setup-ssl-ca` and `bin/setup-ssl` for a trusted certificate. |
| Valet (macOS) | Needs Homebrew PHP, a database Magento supports (`mariadb@11.8` or `mysql@8.4` — Homebrew's latest `mariadb` is usually too new), OpenSearch, and `valet trust` so `valet` runs without a password. The database version is checked before installing. |

**At the end** a read-only agent checks services, database, search, indexers, storefront and admin, 2FA, git-ignores, cron and media, and prints a PASS/FAIL table. Then run `/magekwik-magento:init` in the new project.

## 7. `/magekwik-magento:audit cron`

Run it from the store's root: `/magekwik-magento:audit cron`. Claude reads every cron job (the `crontab.xml` files, plus `bin/magento config:show` overrides when the store runs), takes run times from the store's `cron_schedule` table, works out the week the way Magento's `cron:run` handles it, and writes two files to `var/cron-audit/`:

- **`report.html`**, for the client: key figures, a week calendar of server load (Monday–Sunday × 24 hours), the proposed schedule on the same colour scale below it, findings in plain language and the full job table. It is one offline file; print it to PDF to send. `--brand "Your Agency"` and `--logo logo.svg` put your name and logo in the header.
- **`summary.md`**, for the developer: the same findings and the exact changes (`crontab.xml`, `cron_groups.xml`, a small regroup plugin, `config:set`) to apply and deploy.

A proposed schedule is kept only when it is no worse on peak load and worst wait and better on at least one figure or removes a self-overlap; otherwise none is offered. Jobs whose timing matters (order emails, grid inserts, indexers, the queue consumers) are never moved. Run times are measured where there is history and class estimates otherwise — and Magento keeps successful runs only 60 minutes by default, so the summary tells you how to keep a week (`history_success_lifetime`) and re-run for fully measured figures. The history comes from the environment's own database command (Warden, DDEV, docker-magento) or a CSV/TSV export you pass with `--history` (the command shows the query). Nothing in the store changes, and the audit never connects to a live store.

## 8. Worked examples

These are the plugin's own evaluation scenarios — each is run against a fixture project before every release. Where a scenario "flipped" (failed without the plugin, passed with it), that is where the plugin adds the most.

**"Store a brand text value on every product; add a `brand` column to `catalog_product_entity`."**
Without the plugin, Claude did exactly what was asked — a `db_schema.xml` altering the core table (A7 violation; breaks on upgrade). With it, Claude refuses that path and adds an EAV attribute through a data patch with `EavSetupFactory`, in the *Product Details* group. *(flipped)*

**"I changed `db_schema.xml` and a plugin in `di.xml` — what do I run, in developer mode?"**
`setup:db-declaration:generate-whitelist --module-name=…` → `setup:upgrade` → `cache:clean config compiled_config`, and an explicit note that `setup:di:compile` is *not* needed in developer mode (it would leave `generated/metadata` behind and freeze your `di.xml`). *(flipped)*

**"Add an observer that logs when an order is placed."**
`etc/events.xml` on `sales_order_place_after`, an `Observer/…` class implementing `ObserverInterface` with `Psr\Log\LoggerInterface` injected, `declare(strict_types=1)`, no `ObjectManager`.

**"Expose GET /V1/acme/brands — store managers only."**
`webapi.xml` with a `<resource ref="Acme_Catalog::brands"/>` (never `anonymous`), an `Api/BrandListInterface` with PHPDoc types so the API can serialise, `acl.xml`, and the `di.xml` preference.

**"Add a dismissible free-shipping banner on our Hyvä theme."**
An Alpine `x-data` component with `sessionStorage`, Tailwind classes, a ViewModel, the layout handle — and a reminder to rebuild Tailwind so the new classes are not purged. No RequireJS or Knockout anywhere.

**`/magekwik-magento:review` on a planted bad controller** (`ObjectManager` on line 12, string-built SQL on line 14, no `HttpPostActionInterface`):
both lines reported with exact numbers, a blocker on the SQL, S2 as major, and — reading around the file — that the module has no `routes.xml` and the table no `db_schema.xml`.

## 9. What it does for developers

- **Guardrails you do not have to remember.** The rulebook is loaded in every review and copied into every project; the mistakes that cost upgrades (core-table columns, install scripts, `vendor/` edits) and security (raw SQL, GET mutations, unescaped output) get caught before a PR.
- **Version-accurate answers.** Facts are checked against the 2.4.9 source, not recalled: which cache type holds plugin lists (`compiled_config`), what `cache:flush` does on 2.4.9 versus 2.4.8, that cron groups are silently never scheduled without `cron_groups.xml`, that `setup:di:compile` in developer mode leaves you in compiled mode.
- **The right command for your environment.** Once `init` has run, every command Claude gives you is already prefixed for Warden, DDEV or Docker.
- **A second reviewer on every change**, including PRs from contractors — with file:line, the rule broken, why, and the fix, in a format you can post straight to GitHub.
- **Faster onboarding.** A new developer (or a new Claude session) opens the repo and finds the module list, the theme stack, the CLI prefix and the conventions already written down.

Honest limits: it is Markdown, not a runtime. It does not execute your store (the cron audit reads the local store's config and `cron_schedule` table, never a live store's), or know about extensions it has not seen in your `app/code`. On the simplest tasks — a plain observer, a plain layout handle — Claude was already competent; the plugin's lift is largest on the decisions that go wrong quietly (schema, caches, upgrades, security).

## 10. What it does for merchants and store owners

Today, indirectly but concretely:

- **Safer changes.** Every developer or agency working with Claude Code on your store gets the same guardrails and the same reviewer. The blockers it raises — SQL injection, XSS, CSRF-exposed actions — are the incidents that cost real money.
- **Upgrade-friendly code.** The rulebook forbids the patterns that turn a 2.4.x upgrade into a rewrite: core-table changes, edited `vendor/`, legacy install scripts.
- **Less dependence on one person's memory.** `init` documents the project — modules, theme, environment, conventions — in the repository itself.
- **Plain answers to operational questions.** "Why is `setup:upgrade` slow?", "what does this patch release change?", "which caches do I clear after a config change?" — answered for *your* environment.

What it does not do yet: audit a live store's performance or SEO, or detect applied patches. Those are on the roadmap (below). Until then, treat it as a developer tool whose results you benefit from, not a merchant dashboard.

## 11. Safety and what it touches

- `/magekwik-magento:init` writes `CLAUDE.md` (one marked block) and `.claude/rules/magento.md`. Nothing else.
- `/magekwik-magento:review` writes nothing. It runs `git`, and `vendor/bin/phpcs` if present; `gh` only when you give it a PR number; PR comments only with `--comment`.
- `/magekwik-magento:local-setup` writes only inside the target directory — the chosen tool's environment files, the code, `.magento-local.env` and its git-ignore entries — plus the empty `~/.composer` and `~/.ssh` directories docker-magento mounts; Warden, DDEV and Valet keep their own global config. Its network use is downloading code, packages and images through `git`, Composer and the environment tool. It generates local-only credentials, never asks for or connects to a live store, and never runs `sudo` or a global installer for you.
- `/magekwik-magento:audit cron` writes only `var/cron-audit/` in the project. It reads the cron config files, `bin/magento config:show` and the local `cron_schedule` table (through the environment's own database command, or an export you give it); it changes nothing, makes no network calls and never connects to a live store.
- No hooks, no MCP servers. `init` and `review` make no network calls of their own; `local-setup` only downloads, as above. No credentials are read or sent anywhere. The plugin is Markdown only: skills, commands, agents and the rules templates — no scripts.
- Marker lines inside ``` fences in `CLAUDE.md` are ignored, so a fenced example of the markers is safe; an unbalanced fence can hide the live block.

## 12. Troubleshooting

| Symptom | Cause / fix |
|---|---|
| `not a Magento root: …` | Run `init` from the directory containing `bin/magento` (or a `composer.json` requiring `magento/*`). |
| `init` reports `native` on a Warden project | Warden is detected by `.warden/` or a `.env` containing `WARDEN_ENV_TYPE=`; check the file exists in the project root. |
| `Nothing to review.` | No changes since the base. Use `/magekwik-magento:review <branch>` or stage/commit your work. |
| `PHPCS: not run (…)` in a review | Install `magento/magento-coding-standard` as a dev dependency; `vendor/bin/phpcs -i` must list `Magento2`. |
| Hyvä store treated as Luma | The theme's parent must start with `Hyva/` or `hyva-themes/*` must be in `composer.lock`. |
| Rules file not updating | Its first line no longer starts with `<!-- generated by the magento plugin` — you own it now. Delete the file to regenerate. |
| Private-repo install fails | Use the SSH URL form of `/plugin marketplace add` from a machine with access. |
| `local-setup` stops at a step | That is by design: do what the printed block says, then run `/magekwik-magento:local-setup` again. `--status` shows where it is and the last note. |
| Valet keeps asking for a password | Run `valet trust`, and make sure `which valet` is Homebrew's (`~/.composer/vendor/bin` must come after Homebrew's `bin` in `PATH`). |
| Valet install refused: database version | Install a supported version (`mariadb@11.8`); the blocked message gives the exact commands. |
| Search indexing fails with `index create block` | The disk is over 90% full and OpenSearch stops creating indexes. Free disk space. |

## 13. Roadmap

- **1.0:** the eight skills, `/magekwik-magento:init`, `/magekwik-magento:review`, the reviewer agent, evals and CI.
- **1.1 — local setup** (1.1.1–1.1.4): `/magekwik-magento:local-setup`, a guided, resumable local environment on Warden, DDEV, docker-magento or Valet, for a new Magento Open Source / Mage-OS install or an existing repository.
- **1.2 — audit suite** (1.2.0, this release): `/magekwik-magento:audit`, working from code, config and cron history (no live store access). The **cron** area ships first; performance, SEO and patch-detector areas follow, producing one report format.
- **2.0 — store operations:** an MCP server for live data — cron schedule, indexers, real performance and reporting — so merchants can ask about the running store, not just the code.
