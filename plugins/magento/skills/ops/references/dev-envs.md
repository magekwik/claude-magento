# Development environments: Warden, DDEV, docker-magento, Docker Compose, native

*Target: Magento Open Source 2.4.4–2.4.9, PHP 8.1–8.5 (support varies by release).* Rules cited by ID are in `magento:conventions` (L5 build output is never committed).

Magento's CLI, Composer, `php`, `grunt`/`npm` and MySQL clients must run where the code's PHP and services live. In every containerised setup that is *inside* the PHP container: running `bin/magento` on the host against a container database fails with `SQLSTATE[HY000] [2002] … getaddrinfo for db failed` (the `db` host name only resolves inside the Docker network), and a host Composer writes `vendor/` with the wrong PHP version and user. Detect the environment first, then use its prefix for every command in this skill (`$MAGE` in `SKILL.md`).

## Detection and command prefixes

| Environment | Detection marker (project root) | `bin/magento` prefix | Shell into PHP | DB access | Logs |
|---|---|---|---|---|---|
| **Warden** | `.warden/` directory and/or `.env` containing `WARDEN_ENV_TYPE=magento2` (`WARDEN_ENV_NAME=<name>`) | `warden env exec php-fpm bin/magento` | `warden shell` (php-fpm container, as the `www-data` user, cwd `/var/www/html`) · `warden debug` (php-debug container with Xdebug) | `warden db connect` (mysql client) · `warden db import < dump.sql` · host: connect to the `db` service via the Traefik-published port shown in `warden env config` | `warden env logs --tail 0 -f nginx php-fpm php-debug` · `var/log/*` in the project (bind-mounted) |
| **DDEV** | `.ddev/config.yaml` (with `type: magento2`, `docroot: pub`) | `ddev exec bin/magento` (equivalently `ddev magento`) | `ddev ssh` (web container, cwd = project) · `ddev ssh -s db` | `ddev mysql` · `ddev import-db --file=dump.sql.gz` · `ddev export-db` · from the host: `ddev describe` prints the published DB port; credentials `db`/`db`/`db`, host `db` inside | `ddev logs [-f]` (nginx + php-fpm) · `ddev logs -s db` · `var/log/*` in the project |
| **docker-magento** (markshust) | `compose.yaml` + `compose.dev.yaml` + `bin/` helper scripts (`bin/magento`, `bin/cli`, `bin/clinotty`, `bin/setup`, `bin/start`; `/magento:init` detects it as a compose file plus `bin/clinotty`); code lives under `src/` and is synced into the `phpfpm` container | `bin/magento` (the project's wrapper script — it runs `bin/magento` inside `phpfpm`; do not prefix it further) | `bin/bash` · `bin/cli <cmd>` (non-interactive) · `bin/root <cmd>` · `bin/debug-cli <cmd>` (Xdebug container) | `bin/mysql` (uses `env/db.env`) · `bin/mysqldump > magento.sql` · `bin/mysql < magento.sql` | `bin/log [debug.log]` (tails `var/log` inside the container) · `bin/docker-compose logs` |
| **Docker Compose (hand-written)** | `docker-compose.yml`, `docker-compose.*.yml`, `compose.yml` or `compose.yaml` with a PHP service and no `.warden/`/`.ddev/`/`bin/clinotty` | `docker compose exec <php-service> bin/magento` — the service name varies (`php`, `php-fpm`, `phpfpm`, `app`, `web`…): read it from the compose file's `services:` block; `docker compose ps --services` lists them; use `docker-compose` (hyphen) only where Compose v1 is still installed | `docker compose exec <php-service> bash` (add `-u <user>` when the image runs PHP as a non-root user; `-w /var/www/html` if the working dir is not set) | `docker compose exec <db-service> mysql -u<user> -p<pass> <db>` · `docker compose exec -T <db-service> mysql … < dump.sql` | `docker compose logs -f <php-service> <web-service>` · `var/log/*` where the project directory is bind-mounted |
| **Native** (PHP, MySQL/MariaDB, OpenSearch installed on the host or a VM you are inside) | none of the above; `bin/magento` runs directly and `app/etc/env.php` `db/connection/default/host` is `localhost`/`127.0.0.1`/a reachable host | `bin/magento` | — (you are already there; run as the file-system owner: `sudo -u <owner> bin/magento …`) | `mysql -h<host> -u<user> -p <db>` with the credentials from `app/etc/env.php` (`bin/magento config:show` does not print them; read the file) | `var/log/*`, `var/report/*`; PHP-FPM and web-server logs under `/var/log/` or `journalctl -u php8.x-fpm` |

When two markers are present (a Warden project that also carries a `docker-compose.yml` for something else, docker-magento's `compose.yaml` next to `bin/`), the more specific tool wins: Warden > DDEV > docker-magento > plain Compose. In CI or a `claude -p` run with no TTY, pass `-T` to Warden (`warden env exec -T php-fpm bin/magento …`) and `-T` to Compose (`docker compose exec -T …`); DDEV needs nothing extra.

## Warden

- Project config: `.env` (committed; `WARDEN_ENV_NAME`, `WARDEN_ENV_TYPE=magento2`, `TRAEFIK_DOMAIN`, `TRAEFIK_SUBDOMAIN`, service toggles `WARDEN_DB=1`, `WARDEN_OPENSEARCH=1`, `WARDEN_VARNISH=1`, `WARDEN_REDIS=1`, `WARDEN_RABBITMQ=1`, versions `PHP_VERSION=8.3`, `MYSQL_DISTRIBUTION=mariadb`, `MYSQL_DISTRIBUTION_VERSION=10.6`, `OPENSEARCH_VERSION`, `NODE_VERSION`, `COMPOSER_VERSION`, `PHP_XDEBUG_3=1`). `.warden/warden-env.yml` (and `.warden/warden-env.darwin.yml`/`.linux.yml`) are Compose overrides — extra services, `php.ini` overrides via `.warden/php/zz-config.ini`, nginx snippets via `.warden/nginx/`.
- Lifecycle: `warden env-init <name> magento2` (creates `.env`), `warden env up`, `warden env stop|start`, `warden env down -v` (destroys volumes), `warden env config` (resolved Compose file), `warden doctor`.
- Services by name: `php-fpm`, `php-debug`, `nginx`, `db`, `redis`/`valkey`, `opensearch`/`elasticsearch`, `varnish`, `rabbitmq`. `warden env exec -T varnish varnishlog`, `warden redis flushall`, `warden env exec -T varnish varnishadm 'ban req.url ~ .'`.
- Hostnames inside the containers match the service names — `env.php` uses `db`, `redis`, `opensearch`, `rabbitmq`; the store URL is `https://<TRAEFIK_SUBDOMAIN>.<TRAEFIK_DOMAIN>/` via Traefik with a locally signed certificate (`warden sign-certificate <domain>`).
- Composer runs inside `warden shell` (or `warden env exec php-fpm composer …`); `~/.composer/` is mounted from the host so credentials and cache are shared. Node/Grunt also run inside (`NODE_VERSION`).
- Xdebug: `php-debug` container, routed by the `XDEBUG_SESSION` cookie; `warden debug` for CLI; port 9003 with `PHP_XDEBUG_3=1` (9000 for Xdebug 2). See `references/debugging.md`.
- File sync (macOS): Warden syncs the project into the container with Mutagen and deliberately excludes `pub/static`, `pub/media`, `var/` and `generated/` — they exist only inside the container, never on the host.
- On a brand-new environment `bin/magento setup:install` fails with `Missing write permissions to the current directory (…/pub/static)` until those directories are created inside the container: `warden env exec php-fpm mkdir -p pub/static pub/media var generated`.
- Their contents are not visible on the host — read logs with a command that runs inside the container (`warden env exec php-fpm tail -f var/log/system.log`), not host `tail`/`ls`.
- `warden sync list` shows sync session state and reports `Watching for changes` once the initial sync of a full install (a few minutes) has settled; `warden sync pause`/`warden sync resume` stop and restart it.

## DDEV

- Project config: `.ddev/config.yaml` (`type: magento2`, `docroot: pub`, `php_version`, `database`, `nodejs_version`, `upload_dirs: [media]`, `disable_settings_management`); add-ons such as `ddev add-on get ddev/ddev-opensearch` add services; `.ddev/php/*.ini` overrides PHP settings; `.ddev/docker-compose.*.yaml` adds services.
- Lifecycle: `ddev config --project-type=magento2 --docroot=pub --upload-dirs=media --disable-settings-management`, `ddev start`, `ddev stop`, `ddev restart`, `ddev describe` (URLs, published ports, Mailpit), `ddev launch [/admin_ddev]`.
- `ddev magento …` is a shortcut for `ddev exec bin/magento …`; `ddev composer …` runs Composer inside the web container (`ddev composer create-project --repository https://repo.magento.com/ magento/project-community-edition`); `ddev php`, `ddev npm`, `ddev exec` for anything else. Hostnames inside: `db`, `opensearch` (from the add-on); the site is `https://<name>.ddev.site/`. Settings management is disabled for Magento 2 so DDEV never rewrites `env.php` — set `db-host=db --db-name=db --db-user=db --db-password=db` yourself in `setup:install`.
- Composer credentials: symlink or copy `auth.json` into `$HOME/.ddev/homeadditions/.composer/auth.json` so every project sees them.
- Xdebug: `ddev xdebug on|off|toggle|status`; off by default. See `references/debugging.md`.

## docker-magento (Mark Shust)

- Layout: `compose.yaml` + `compose.dev.yaml` (+ optional `compose.override.yaml`, `compose.versions.yaml` pinned by `bin/detect-versions`), `env/*.env` (`db.env`, `magento.env`, `phpfpm.env`…), `bin/` wrapper scripts, application under `src/`. Services: `app` (nginx), `phpfpm`, `phpfpm-xdebug`, `db`, `redis`/`valkey`, `opensearch` (or `elasticsearch`), `rabbitmq`, `mailcatcher`.
- The wrappers *are* the prefix: `bin/magento`, `bin/composer`, `bin/n98-magerun2`, `bin/node`, `bin/npm`, `bin/grunt`, `bin/phpcs`, `bin/phpcbf`, `bin/mysql`, `bin/mysqldump`, `bin/redis`, `bin/cli <cmd>`, `bin/clinotty <cmd>` (no TTY — use it from scripts and CI), `bin/root`, `bin/bash`, `bin/log`, `bin/status`, `bin/start`/`bin/stop`/`bin/restart`, `bin/removeall`, `bin/deploy [locale]` (the production command sequence), `bin/cache-clean` (the mage2tv cache-clean watcher, started automatically by `bin/start`), `bin/devconsole`, `bin/fixowns`/`bin/fixperms`, `bin/setup <domain>`, `bin/setup-domain`, `bin/setup-ssl`, `bin/update` (pulls a newer template — keep local changes in `compose.override.yaml`).
- File sync: the code lives in a Docker volume for speed; `bin/copytocontainer --all` after cloning or editing outside the IDE sync, `bin/copyfromcontainer vendor` (or `var/log`) to pull generated files back; `src/` on the host mirrors the container. Newer versions (≥ 40) can instead mount over SSH/SFTP from the IDE.
- Xdebug: `phpfpm-xdebug` container via the `XDEBUG_SESSION` cookie, `bin/debug-cli <cmd>` for CLI, `bin/setup-nginx` to enable cookie routing on older projects, `bin/configure-linux` for the Linux firewall/hosts. `bin/xdebug` is deprecated.

## Plain Docker Compose

Read the compose file before assuming anything: the PHP service name, the working directory (`working_dir:` or the image's default, usually `/var/www/html`), the user PHP runs as (`user:` or the image's `www-data`/`app`), where the project is mounted (`volumes:` — a bind mount means `var/log` and `generated/` are visible on the host; a named volume means they are not), and whether Composer exists in the image (`docker compose exec <php-service> composer --version`; if not, run it through a one-off `docker run --rm -v "$PWD":/app -w /app composer:2 …` with the same PHP major). Environment variables for Magento (`MAGE_MODE`, `MAGE_RUN_CODE`, `CONFIG__DEFAULT__…`) are usually in the service's `environment:` block or an `env_file:`; database credentials in `env.php` refer to the DB service name. `docker compose exec` needs a running container; `docker compose run --rm <php-service> bin/magento …` starts a throwaway one (no nginx needed for CLI). Xdebug depends entirely on the image — check `php -m | grep -i xdebug` inside it.

## Native

`bin/magento` runs directly, as the file-system owner (`sudo -u www-data bin/magento …` or a shared-group setup); `php -v` must be the PHP version the web server uses (a system with several PHP versions needs `php8.3 bin/magento …` or an `update-alternatives` choice). The `php.ini` that applies to the CLI is separate from PHP-FPM's — `memory_limit`, `max_execution_time` and `xdebug.*` must be set in both (`php --ini` shows which files load). Services are reached over `localhost`; `env.php` hosts are `127.0.0.1`/`localhost`. Cron is the owner's crontab (`crontab -l` shows the `#~ MAGENTO START` block). This is also what you are in when you `warden shell`/`ddev ssh`/`bin/bash` into a container: from inside, no prefix.

## Composer inside vs outside the container

Composer must run with the same PHP major/minor as the runtime (the lock file's `platform` and `require.php` are checked at install) and as the file owner that PHP uses — so inside the container for Warden, DDEV, docker-magento and Compose, and as the file-system owner natively. Credentials for `repo.magento.com` come from `auth.json` in the project root (git-ignored) or `COMPOSER_AUTH`; Warden mounts `~/.composer`, DDEV reads `$HOME/.ddev/homeadditions/.composer/auth.json`, docker-magento copies `src/auth.json` in with `bin/copytocontainer auth.json`. `composer install` writes `vendor/`, `generated/` may need clearing afterwards, and `bin/magento setup:upgrade` follows every dependency change (`SKILL.md`).
